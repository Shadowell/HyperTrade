# Feature Specification: 进化告警与修复需求

**Feature Branch**: `codex/evolution-alert-reliability`
**Created**: 2026-09-21
**Status**: R1–R3 已实现并完成生产复验；R4–R7 保留后续依赖
**Input**: 用户要求此类阻塞都应告警，解释未看到的原因，整理需求并逐步修复。

## User Scenarios & Testing
### US1 通知可信且持续（Priority: P1）
验收：业务拒绝不得显示送达；未解决未确认每24小时提醒；确认或恢复后停止；重复 tick 不重复通知。
### US2 页面能看到需要处理的问题（Priority: P1）
BitPro 页面显示未解决告警、中文原因、投递状态、最近通知和确认入口；读取失败明确显示。
### US3 读取失败可以定位（Priority: P1）
高频采样不能只显示不可用，必须区分容量、成本、身份、传输失败；不重建原会话。
### Edge Cases
HTTP200但业务拒绝、无效JSON、超时、未配置渠道、旧sent无回执、重启、恢复重现、原因变化与旧告警遮盖新问题。

## Requirements
### Functional Requirements
- FR-001：通知成功必须有业务成功回执；服务接受不等于用户已读。
- FR-002：未确认未解决每24小时提醒，失败6小时节流继续重试，不在7天后静默放弃；缺渠道不计尝试。
- FR-003：通知包含中文原因、策略ID、下一步和时间条件，持续原因变化更新内容。
- FR-004：BitPro接入认证告警列表/确认，优先展示未解决；旧sent显示回执未验证。
- FR-005：诊断保存稳定、脱敏错误类别与HTTP状态；修复高频点数容量，不伪造历史成本。
- FR-006：需求表区分立即修复与依赖真实观察/外部平台项目；不默改策略范围和评审政策。
- FR-007：最新有效手动诊断及时更新告警；过期、旧revision或早于自动检查的报告不覆盖；不改变研究准入。
### Key Entities
沿用 EvolutionAlert 生命周期、投递回执、提醒计数与 continuation 资格/阻塞记录。

## Success Criteria
- SC-001：投递拒绝、提醒、确认、恢复重现和高频读取有确定性回归。
- SC-002：现有飞书通道取得真实业务成功回执，BitPro可见同一告警。
- SC-003：原Paper会话/版本/起点不变，检查通过且部署SHA可核对。

## Assumptions
复用现有飞书群，用户已授权此类告警通知；每天提醒直到确认或恢复。
保留 human 审核和策略范围；不启动额外付费评测。
