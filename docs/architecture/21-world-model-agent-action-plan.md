# 世界模型驱动策略 Agent 行动纲领

## 1. 文档目的

这份文档用于指导另一个 agent 继续设计或实现一个「世界模型驱动的策略决策系统」。

这里的 agent 不应被理解为一个直接回答买卖问题的聊天助手，而应被设计成一个持续维护状态、推演行动后果、遵守约束、记录结果并根据反馈修正判断的策略操作系统。

本阶段的目标不是立刻实现完全自动交易，而是先建立一套可观察、可解释、可审计、可逐步放权的决策框架。

## 2. 核心定义

### 2.1 世界模型

世界模型是 agent 对当前环境的结构化理解。它至少需要回答以下问题：

- 当前市场、账户、策略和系统分别处于什么状态
- 哪些变量正在影响当前状态
- 如果不采取行动，状态可能怎样演化
- 如果采取某个行动，可能带来哪些收益、风险和副作用
- 当前判断的置信度是多少
- 哪些信息缺失，是否需要继续观察或请求人工确认

在这个语境里，世界模型不是知识库，也不是单纯的历史记录。它是一个可以支持预测和行动的状态压缩层。

### 2.2 策略 Agent

策略 agent 是围绕世界模型工作的决策单元。它的职责包括：

- 观察市场、账户、策略、订单和系统状态
- 将原始信息压缩成可决策的 `WorldState`
- 基于候选动作推演可能后果
- 对动作进行收益、风险、置信度和权限评估
- 在约束范围内执行动作，或请求人工确认
- 记录决策、执行和结果，用于后续复盘

## 3. 设计原则

### 3.1 先建状态，再做决策

agent 的第一项能力不是下单，而是稳定维护当前世界状态。

任何建议、告警或执行动作，都必须能回溯到当时的 `WorldState`。如果系统无法说明「它当时看到了什么」，就不应该扩大它的自动执行权限。

### 3.2 LLM 负责解释和编排，确定性模块负责放行

LLM 可以承担复杂上下文理解、异常解释、方案比较、工具编排和自然语言输出。

关键动作需要经过确定性模块验证，包括：

- 风控规则
- 权限系统
- 仓位限制
- 订单模拟器
- 执行网关
- 审计日志

推荐执行顺序：

```text
LLM 提出动作
规则系统检查动作是否合法
模拟器推演账户和仓位变化
风控系统判断是否放行
执行器执行动作
审计模块记录证据
```

### 3.3 先自动防守，再自动进攻

早期 agent 应优先支持防守型动作，例如：

- 识别数据异常
- 发现订单卡住
- 提醒仓位过重
- 降低杠杆
- 暂停策略
- 撤销异常挂单
- 请求人工确认

进攻型动作，例如主动开仓、加仓、切换高风险参数，应在有足够复盘数据和权限控制之后再逐步开放。

### 3.4 每次决策都必须留下证据

任何一次建议或动作都要记录：

- 当时的 `WorldState`
- 候选动作列表
- 每个动作的评估结果
- 最终选择的动作
- 决策理由
- 风控检查结果
- 执行结果
- 后续真实结果
- 判断是否正确，以及错误来自哪里

不能复盘的行为，不应进入自动化。

## 4. Agent 需要的信息

### 4.1 市场状态

需要采集的信息包括：

- 最新价格
- K 线和成交量
- 波动率
- 流动性
- 买卖盘深度
- 资金费率
- 基差
- 相关资产走势
- 市场 regime，例如趋势、震荡、高波动、低流动性、事件驱动

目标不是堆叠指标，而是判断当前行情是否适合某个策略继续运行。

### 4.2 策略状态

需要采集的信息包括：

- 当前策略名称和版本
- 策略参数
- 当前信号
- 信号强度
- 最近信号命中率
- 最近回撤
- 当前策略是否处于预期适用环境
- 策略最近是否出现失效迹象

agent 应能区分「策略正常亏损」和「策略假设可能失效」。

### 4.3 账户状态

需要采集的信息包括：

- 总权益
- 可用资金
- 保证金占用
- 当前杠杆
- 未实现盈亏
- 已实现盈亏
- 当前风险敞口
- 单品种和组合层面的仓位比例
- 距离风控阈值还有多远

账户状态用于判断系统是否还有继续承担风险的能力。

### 4.4 仓位和订单状态

需要采集的信息包括：

- 当前持仓方向
- 持仓数量
- 开仓均价
- 当前浮盈浮亏
- 止损和止盈设置
- 未成交挂单
- 最近成交记录
- 滑点
- 失败订单
- 撤单记录

这部分信息用于识别执行风险，例如订单卡住、重复下单、滑点异常和仓位失控。

### 4.5 系统状态

需要采集的信息包括：

- 行情数据是否延迟
- 数据源是否可用
- 交易接口是否正常
- 风控服务是否正常
- 订单执行通道是否正常
- 最近错误日志
- 关键任务是否按时运行

如果系统状态异常，agent 应优先降级或暂停，而不是继续做市场判断。

### 4.6 外部事件状态

可选采集的信息包括：

- 宏观事件
- 新闻
- 交易所公告
- 链上异常
- 大额转账
- 政策变化
- 高影响财经日历

LLM 适合在这一层做语义解释，但解释结果仍应转化成结构化标签和置信度。

### 4.7 记忆和复盘状态

需要记录的信息包括：

- 过去相似场景
- 当时采取的动作
- 当时的判断理由
- 后续真实结果
- 哪些信号有效
- 哪些信号失效
- 哪些风控规则避免了损失
- 哪些判断经常误伤策略

记忆不是自由文本聊天记录，而应尽量结构化，便于检索和统计。

## 6. 决策循环

推荐使用固定循环：

```text
Observe -> BuildState -> Simulate -> Score -> Decide -> Act -> Review -> Learn
```

### 6.1 Observe

采集市场、账户、策略、订单、系统和外部事件信息。

这一层只负责拿到事实，不做过多解释。

### 6.2 BuildState

把原始信息压缩成 `WorldState`。

这一层需要输出当前状态标签，例如：

- 市场 regime
- 策略健康度
- 账户风险等级
- 系统可用性
- 当前是否允许自动执行

### 6.3 Simulate

对候选动作做情景推演。

至少比较以下动作：

- 继续持有
- 减仓
- 平仓
- 暂停策略
- 加仓
- 请求人工确认
- 继续观察

每个动作都需要推演：

- 预期收益
- 最大可能损失
- 对保证金和杠杆的影响
- 对组合风险的影响
- 对后续可操作空间的影响
- 失败后的处理方式

### 6.4 Score

对每个候选动作打分。

推荐评分维度：

- 预期收益
- 下行风险
- 置信度
- 是否符合当前策略目标
- 是否触发风控限制
- 是否需要人工确认
- 执行复杂度
- 可回滚性

### 6.5 Decide

选择动作时，需要输出结构化结果。

```json
{
  "decision": "reduce_position",
  "target": "BTCUSDT",
  "size_change": "-30%",
  "reason": "市场波动升高，策略信号仍有效，但账户风险等级已接近高风险区间。",
  "confidence": 0.72,
  "requires_human_confirmation": true,
  "risk_check": "passed",
  "review_after": "30m"
}
```

如果信息不足，正确动作可以是 `observe_more` 或 `request_human_confirmation`。

### 6.6 Act

执行动作前必须经过权限和风控检查。

建议将动作分成四个权限等级：

- L0：只读观察和报告
- L1：生成建议，但不执行
- L2：允许低风险防守动作，例如暂停策略、撤异常挂单、降低仓位上限
- L3：允许进攻型动作，例如主动开仓、加仓、策略切换

早期系统应停留在 L0 到 L1。L2 和 L3 必须通过复盘数据和稳定性验证后再开放。

### 6.7 Review

动作执行后，需要在固定时间窗口复盘。

复盘问题包括：

- 预测是否命中
- 风险是否降低
- 收益是否符合预期
- 是否出现未预期副作用
- 执行是否成功
- 是否需要更新规则或记忆

### 6.8 Learn

把复盘结果写入记忆系统。

记忆内容应尽量结构化，例如：

```json
{
  "case_id": "string",
  "world_state_summary": "高波动趋势行情，账户风险接近阈值",
  "decision": "reduce_position",
  "expected_outcome": "降低回撤和保证金压力",
  "actual_outcome": "回撤下降，后续少赚部分趋势收益",
  "lesson": "高波动趋势中，减仓比完全平仓更适合保留策略暴露。",
  "confidence_update": "+0.05"
}
```

## 7. 组件拆分

不要把系统做成一个全能 agent。推荐拆成以下组件。

### 7.1 Observer

职责：

- 采集市场数据
- 采集账户数据
- 采集策略运行状态
- 采集订单和系统健康状态
- 采集外部事件

输出：

- 原始事实
- 数据新鲜度
- 数据源健康状态

### 7.2 State Builder

职责：

- 将原始信息转成 `WorldState`
- 标注市场 regime
- 标注账户风险等级
- 标注策略健康状态
- 标注系统可用性

输出：

- `WorldState`
- 关键状态解释
- 缺失信息列表

### 7.3 Simulator

职责：

- 接收 `WorldState` 和候选动作
- 推演动作后果
- 估算风险和收益
- 识别动作副作用

输出：

- 每个动作的情景推演结果

### 7.4 Risk Officer

职责：

- 检查动作是否合法
- 检查是否超过仓位限制
- 检查是否触发风控规则
- 判断是否需要人工确认
- 在系统异常时拒绝交易动作

输出：

- `approved`
- `rejected`
- `requires_human_confirmation`
- 拒绝或确认原因

### 7.5 Executor

职责：

- 执行已经放行的动作
- 写入审计日志
- 处理执行失败
- 返回执行结果

输出：

- 执行状态
- 成交或失败详情
- 滑点和延迟信息

### 7.6 Reviewer

职责：

- 对决策结果做复盘
- 比较预测和真实结果
- 记录错误类型
- 生成可用于后续检索的经验

输出：

- 复盘记录
- 规则修正建议
- 记忆更新

## 8. Agent 输出格式

另一个 agent 在做任何建议时，应尽量使用以下格式。

```text
当前状态：
- 市场：
- 策略：
- 账户：
- 订单：
- 系统：

主要风险：
- 

候选动作：
1. 继续观察
2. 继续持有
3. 减仓
4. 平仓或暂停策略
5. 加仓或切换策略

动作评估：
- 动作：
- 预期收益：
- 下行风险：
- 置信度：
- 风控结果：
- 是否需要人工确认：

最终建议：
- 建议动作：
- 理由：
- 执行条件：
- 回滚方案：
- 复盘时间：
```

这个格式的目的，是避免 agent 只给出结论，而不展示状态、推演和约束。

## 9. 阶段路线

### 阶段一：只读世界模型

目标：

- 不执行任何交易动作
- 汇总市场、账户、策略和系统状态
- 识别市场 regime
- 输出风险报告
- 记录预测和真实结果

验收标准：

- 能稳定生成 `WorldState`
- 能解释当前风险
- 能指出缺失信息
- 能记录预测是否命中

### 阶段二：半自动决策

目标：

- agent 可以提出动作建议
- 所有动作需要人工确认
- 每个建议必须包含情景推演和风控检查结果

验收标准：

- 建议格式稳定
- 风险解释可追溯
- 人工可以快速判断是否采纳
- 建议结果可以进入复盘库

### 阶段三：有限自动执行

目标：

- 允许低风险防守动作自动执行
- 进攻型动作继续保持人工确认

可开放动作：

- 暂停策略
- 降低仓位上限
- 撤销异常挂单
- 降低杠杆
- 触发已定义止损

验收标准：

- 每个自动动作都有审计记录
- 自动动作没有绕过风控
- 执行失败能被识别并上报
- 自动动作确实降低了风险

### 阶段四：多策略调度

目标：

- agent 管理策略组合，而不是单个策略
- 根据市场 regime 调整策略权重
- 识别策略之间的相关性风险
- 发现策略失效并降低资金分配

验收标准：

- 能说明为什么提高或降低某个策略权重
- 能识别组合层面风险
- 能跟踪策略切换后的结果
- 能把策略表现反馈到记忆系统

## 10. 关键约束

实现时必须遵守以下约束：

- 没有 `WorldState`，不允许输出交易动作建议
- 系统状态异常时，优先暂停或请求人工确认
- 风控模块不可由 LLM 绕过
- 所有动作必须写入审计日志
- 所有自动执行权限必须分级开放
- 不允许在无复盘数据的情况下开放高风险自动动作
- 信息不足时，允许并鼓励输出 `observe_more`

## 11. 第一批实现任务

建议另一个 agent 按以下顺序推进：

1. 定义第一版 `WorldState` schema
2. 梳理现有数据源能提供哪些字段
3. 标记缺失字段和替代字段
4. 实现只读 `Observer`
5. 实现 `State Builder`
6. 实现基础市场 regime 识别
7. 实现账户风险等级计算
8. 实现候选动作模板
9. 实现动作评分格式
10. 实现决策记录和复盘记录

第一阶段不要接交易执行网关。先验证状态建模、推演和复盘是否稳定。

## 12. 推荐的最小可用版本

最小可用版本应具备以下能力：

- 每隔固定时间生成一次 `WorldState`
- 输出当前市场 regime 和置信度
- 输出账户风险等级
- 输出策略健康状态
- 比较至少四个候选动作：继续观察、继续持有、减仓、暂停策略
- 给出动作评分
- 说明是否需要人工确认
- 记录建议和后续结果

如果这一版稳定，再考虑接入低风险自动动作。

## 13. 给执行 Agent 的直接指令

你接下来要做的不是写一个会聊天的交易助手，而是设计一个可审计的策略决策系统。

请优先完成以下工作：

1. 用本文的 `WorldState` 作为起点，结合实际项目字段做一次 schema 对齐
2. 明确哪些信息现在能拿到，哪些信息缺失
3. 把 agent 的输出固定成结构化决策格式
4. 先实现只读观察和建议，不要直接接入真实下单
5. 为每次建议保存输入、推演、决策、结果和复盘
6. 等只读建议有足够结果记录之后，再讨论自动执行权限

判断本任务是否完成，不看 agent 能否说出漂亮解释，而看它是否能稳定回答：

- 当前世界状态是什么
- 我能做哪些动作
- 每个动作可能带来什么后果
- 哪个动作在当前约束下更合适
- 我为什么这么判断
- 后续事实是否验证了这次判断
